# AgentSpec

AgentSpec is a small domain-specific language for runtime safety rules on LLM agents: each rule has a **trigger** (an event such as an action about to run), **predicates** over the current state, and an **enforcement action**. Hand-written rules prevented more than 90% of unsafe code executions at millisecond overhead. Its most important number for this product is a failure: rules generated by an LLM (o1) reached 95.56% precision but only **70.96% recall**. Generated policy misses about three hazards in ten, so it must be bounded by a static ceiling and checked for coverage.

## Citation

- Wang, Poskitt, Sun. "AgentSpec: Customizable Runtime Enforcement" (short title as recorded; check the full arXiv title). arXiv 2503.18666; ICSE 2026 ([arXiv](https://arxiv.org/abs/2503.18666)).
- Code: not visible on the abstract page; availability unverified.

## Mechanism

Rules are checked at runtime, around each agent action ([arXiv](https://arxiv.org/abs/2503.18666)):

```text
rule <name>
  trigger:    <event, e.g. before tool "shell" executes>
  check:      <predicate_1> and <predicate_2> ...     # over action args and agent state
  enforce:    <action, e.g. stop | ask user | replace/correct>
```

Illustrative example in the research record's spirit: "before `rm -rf` on a path outside the workspace → deny". The rules are evaluated deterministically; the DSL has no information-flow or data-provenance concepts.

## Threat model and assumptions

- **Primary concern:** unsafe or unreliable agent behaviour (hazardous code execution, unsafe physical actions, traffic-law violations) rather than a specific external attacker ([arXiv](https://arxiv.org/abs/2503.18666)). In this vault's terms that is mostly adversary A3, the misbehaving model.
- **Trusted:** the rule author. When rules are hand-written, their coverage is the developer's responsibility; when rules are LLM-generated, the generator becomes a trusted component whose recall was measured at 70.96%.
- **Assumed:** hazards are enumerable as trigger/predicate pairs over observable state.
- **Adaptive attacks:** none in the record.
- **Code:** not visible on the abstract page (unverified).

## Evidence

From the paper ([arXiv](https://arxiv.org/abs/2503.18666)):

| Domain | Result |
|---|---|
| Code agents | >90% of unsafe code executions prevented |
| Embodied agents | 100% of hazardous actions eliminated |
| Autonomous vehicles | 100% compliance |
| Overhead | Millisecond-scale |
| LLM (o1)-generated rules, embodied | **95.56% precision, 70.96% recall** |
| LLM-generated rules, code | 87.26% risky-code identification |
| LLM-generated rules, AV | 5 of 8 scenarios |

## Counter-evidence and weaknesses

- **Recall of generated rules.** 70.96% recall means roughly 29% of hazards are missed when rules are auto-generated. The research inference: never ship auto-generated rules without a coverage check against a hazard list.
- **No data-flow awareness.** Rules are trigger/predicate lists; they cannot express "the recipient came from untrusted content" ([[Information Flow Control]]).
- **Enumerative safety.** Rules name bad actions; anything not named passes. That is the opposite of a deny-by-default capability grant.
- **No adaptive evaluation** in the record; AgentSpec was not in [[The Attacker Moves Second]] or the June 2026 out-of-band study.

## Where the probabilistic part lives

Rule generation, when rules are LLM-written. Checking is deterministic.

## Why it matters for learned policy

AgentSpec sits in a cluster of LLM-synthesised policy systems: Progent (JSON-Schema rules from the task, SMT-checked narrowing; [arXiv 2504.11703](https://arxiv.org/html/2504.11703)), [[Conseca]] (per-task regex policies with rationales; [arXiv 2501.17070](https://arxiv.org/html/2501.17070v3)), AgentCore Policy (natural language to Cedar, verified by Cedar Analysis; [AWS](https://aws.amazon.com/blogs/security/why-policy-in-amazon-bedrock-agentcore-chose-cedar-for-securing-agentic-workflows/)) and Policy-as-Prompt, which compiles design documents into prompt-based classifiers, so its enforcement stays probabilistic ([arXiv 2509.23994](https://arxiv.org/abs/2509.23994)). AgentSpec is the one that measured recall, and the number is the warning: **a static baseline ceiling must exist independent of generation** (research note 02, Q4 inference). The report cites it directly in the policy-learning decision: "AgentSpec's 71% recall shows generation misses hazards; a static ceiling must bound results" ([[ADR-011 Verified Policy Learning Loop]]).

## Adopt / Improve / Add

- **Adopt:** the trigger → predicate → action shape for **non-IFC safety rules**, for example "before `git.push` with `force=true` → deny" or "before `pkg.publish` → require approval". In Cedar these are ordinary `forbid ... when {...}` rules over adapter verbs ([[Example Cedar Policies]]).
- **Improve:** **Proposal:** never ship generated rules without (1) a coverage check against a hazard list (the conformance probe categories plus org deny lists) and (2) SymCC proof that the result is within the org ceiling, `check_implies(P_new, P_ceiling)` ([[SymCC CI Gates]]). Generated or learned rules are proposals that pass through schema validation, ceiling analysis and diff-based human approval.
- **Add:** **Proposal:** invert the default: rules in this product narrow a deny-by-default grant rather than enumerate bad actions, so a missed hazard stays denied unless something explicitly allowed it. Learn allows from traces ([[Trace-Mined Least Privilege]]) and keep forbids as a hand-maintained ceiling that learning cannot touch ([[Policy Miner Safeguards]]).

## Implications for the build

- M2: `broker learn` and `broker suggest` output is a proposal; it never merges without the SymCC narrowing and ceiling gates, and high-risk verbs are never auto-granted.
- Keep a curated hazard list as a test fixture; measure recall of learned or LLM-drafted policy against it and report the number.
- An LLM may explain a diff but never merge it (I3).
